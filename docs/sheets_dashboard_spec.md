# Google Sheets Data Model & Dashboard — Spec v1

Owner: Claude (architecture/data model/dashboard design, per `PROJECT_BRIEF.md`).
Implementer: Grok (`export_to_sheets.py`, chart setup, automation wiring).
Status: design only — no code written against this yet.

This spec is grounded in the **actual current output columns** of the pipeline
(`out/demand_report.csv`, `out/search_volume_signal.csv`,
`out/printables_cults_signal.csv`, `out/marketplace_signal.csv`,
`out/trends_signal.csv`, `out/x_signal.csv`, `out/reddit_signal.csv`,
`out/local_service_keywords_phoenix_az.csv`,
`out/local_service_market_phoenix_az.json`) as of the `score_demand.py`
rewrite in commit `d537c63`. If those column names change, this spec's
column lists need a matching update before Grok implements against it.

## 0. Deviations from the Project Brief's tab list — flagged up front

The brief lists 7 tabs: Dashboard, Product Rankings, Search Volume, Local
Service (Phoenix), Marketplace, History, Config. I'm keeping all 7 but
adding **one**: **Scoring Detail**. Reason: `demand_report.csv` currently
has ~100 columns (raw scores, normalized scores, per-factor contribution
columns, notes/flags). Cramming all of it into "Product Rankings" makes
that tab unreadable on a phone or a quick Monday check — which defeats the
brief's own success criterion. Splitting it into a trimmed, human-facing
**Product Rankings** tab plus a full-detail **Scoring Detail** tab (for the
"why did this rank #1" question) keeps both goals intact. If you'd rather
fold Scoring Detail back into Product Rankings as hidden columns instead of
a separate tab, that's a fine implementation-level call for Grok — the
column *content* below doesn't change either way.

**Resolved:** `search_volume_keywords.csv` now includes a `product` column
(one row per product×keyword). Older flat files without `product` still
export as a labeled audit list. Phantom product rows from signal-name drift
are blocked in `score_demand.py` (products.yaml is the merge spine).

## 1. Tab structure

### 1.1 Dashboard
See Section 2 for full layout. No raw data lives here — every element
either reads from another tab's range or is precomputed by the pipeline
before upload.

### 1.2 Product Rankings
One row per product, current run only (overwritten each run — history
lives in the **History** tab, not here). Trimmed to what a human needs to
decide "what do I work on":

| Column | Source | Notes |
|---|---|---|
| `rank` | demand_report.csv | 1 = highest priority |
| `product` | demand_report.csv | join key across all tabs |
| `category` | demand_report.csv | niche tag |
| `priority_score` | demand_report.csv | primary sort key |
| `demand_score` | demand_report.csv | |
| `fit_score` | demand_report.csv | manufacturing/customer fit |
| `competition_score` | demand_report.csv | |
| `opportunity_score` | demand_report.csv | |
| `search_volume` | demand_report.csv | monthly, DataForSEO |
| `search_volume_best_keyword` | demand_report.csv | which keyword drove the volume number |
| `cpc_avg` | demand_report.csv | commercial-intent proxy |
| `ads_competition_avg` | demand_report.csv | |
| `total_listings` | demand_report.csv | marketplace saturation |
| `community_downloads` / `community_makes` / `community_likes` | demand_report.csv | Printables+Cults combined |
| `trends_avg_interest_0_100` / `trends_recent_vs_prior_pct_change` | demand_report.csv | |
| `fit_flags` | demand_report.csv | e.g. `fdm_friendly_geometry;pla_petg_ok;clear_platform;simple_part` |
| `score_explanation` | demand_report.csv | one-line human-readable breakdown, already generated by `score_demand.py` |
| `run_date` | pipeline metadata | ISO date this row was generated |

Everything else in `demand_report.csv` (the `n_*`, `contrib_*`, `raw_*`,
`*_notes` columns) goes to Scoring Detail, not here.

### 1.3 Scoring Detail
Audit/debug tab. One row per product per run (can be overwritten each run
like Product Rankings, or appended like History — recommend overwrite,
since this is a "why" lookup for the *current* run, not a trend view).
Columns: `product`, `run_date`, then all remaining `demand_report.csv`
columns not already in Product Rankings — every `contrib_demand_*`,
`contrib_competition_*`, `contrib_fit_*`, `raw_intent`/`intent_notes`,
`raw_specificity`/`specificity_notes`, `raw_problem_intensity`/
`problem_notes`, `raw_volume_quality`, `fdm_fit`, `material_fit`,
`customer_clarity`, `support_burden`, and the `n_*` normalized columns.
Straight passthrough — no new logic needed, just "everything not listed
above."

### 1.4 Search Volume
Two sections in one tab (stacked, not side-by-side — keeps column widths sane):

**Section A — per-product summary** (from `search_volume_signal.csv`):
`product`, `category`, `search_volume`, `search_volume_max`,
`search_volume_sum`, `search_volume_avg`, `search_volume_best_keyword`,
`ads_competition_avg`, `cpc_avg`, `keywords_queried`, `keywords_with_data`.

**Section B — keyword-level audit** (from `search_volume_keywords.csv`):
`product`, `keyword`, `search_volume`, `competition`, `competition_index`,
`cpc`, `low_top_of_page_bid`, `high_top_of_page_bid`, `fetched_at`.
As of the product-link fix in `search_volume_scan.py`, this is **one row
per (product, keyword)** so Sheets can filter by product. Shared keywords
(e.g. a broad seed used by two products) appear once per product; metrics
are identical (cache is still keyword-keyed). Older CSVs without `product`
are still accepted and labeled as a flat audit list.

### 1.5 Marketplace
Combines both "what already exists" sources into one tab per the brief's
naming (listing counts = raw competition count; community engagement =
validated demand-that-already-shipped). From `marketplace_signal.csv` +
`printables_cults_signal.csv`, joined on `product`:

`product`, `category`, `printables_listing_count`, `cults_listing_count`,
`total_listings`, `printables_downloads`, `printables_makes`,
`printables_likes`, `printables_top_downloads`, `printables_top_name`,
`cults_downloads`, `cults_makes`, `cults_likes`, `cults_top_downloads`,
`cults_top_name`, `community_downloads`, `community_makes`,
`community_likes`.

### 1.6 Local Service (Phoenix)
Three stacked sections, translating the existing
`local_service_market_phoenix_az.json` / `.md` shape directly (Grok doesn't
need to invent a new structure — the JSON already has this):

**Section A — keyword demand** (`local_service_keywords_phoenix_az.csv`):
`rank`, `keyword`, `search_volume`, `competition`, `competition_index`,
`cpc`, `low_top_of_page_bid`, `high_top_of_page_bid`, `fetched_at`.

**Section B — People Also Ask** (`local_competitors.json` →
`people_also_ask`): `question`, `source_keyword`.

**Section C — Maps competitors** (`local_competitors.json` →
`local_competitors`): `name`, `rating`, `review_count`, `address`,
`phone`, `url`, `is_claimed`.

Small footer note: API cost for this run (`costs_reported.total_serp_usd`)
— useful since this is metered spend, keeps it visible without digging
into logs.

### 1.7 History
**Append-only.** One row per `(run_date, product)`, never overwritten or
deleted by the pipeline. This is the only tab that grows every run and the
only source for trend charts and week-over-week deltas.

Columns (deliberately narrow — this is a trend-tracking log, not a full
audit): `run_date`, `run_id`, `product`, `category`, `rank`,
`priority_score`, `demand_score`, `fit_score`, `competition_score`,
`opportunity_score`, `search_volume`, `total_listings`,
`community_downloads`.

`run_id` = full timestamp (e.g. `2026-08-02T09:15:00-07:00`), `run_date` =
date only (`2026-08-02`), so day-level grouping doesn't require string
parsing in Sheets formulas.

### 1.8 Config
Read-only, regenerated-each-run **mirror** of `config/products.yaml` +
`config/local_service.yaml`. This tab is for the human to see what's being
tracked without opening the repo — **it is not editable in Sheets and
edits made here do not feed back into the pipeline.** State this
explicitly as a note/comment on the tab itself so it's never mistaken for
a config UI.

Columns: `product`, `category`, `keywords` (joined `"; "`),
`search_volume_keywords_override` (if set), `fit_overrides` (if set, as
`key=value; key=value`), plus a small fixed block for `local_service.yaml`
basics: `city`, `location_name`, `cache_ttl_days`, `seed_keyword_count`.

## 2. Dashboard layout

**Top — status strip (glanceable in 5 seconds):**
- `Last updated: {run_date} {run_time}` — single source of truth, referenced identically by every tab that regenerates each run (see Section 5, "one canonical run-metadata source")
- Data-freshness indicator: green if `run_date` ≤ 8 days old, yellow 8–14, red > 14 (weekly cadence is the target; red means the schedule silently broke)
- "Sources active this run" chips — one per signal (Search Volume, Community, Marketplace, Trends, X, Reddit), each showing active/skipped. This must be sourced from `score_demand.py`'s actual `demand_unused` list for that run (see Section 5) — never inferred from whether a cell happens to be zero
- KPI tiles: products tracked, top `priority_score` this run, count of products newly in the top 10 vs. last run (churn signal), local-service keywords tracked

**Middle — the actual analysis:**
- **Top Opportunities This Week** — top 10 rows from Product Rankings by `priority_score`, showing product, category, the four component scores, and `score_explanation`
- **Demand vs Fit quadrant** — the brief's explicit "Demand vs Fit view" (see chart 1 below)
- **Category/niche comparison** — which niche (rad_power_bikes / mtb_general / drone_fpv / automotive / atv_utv) is winning overall, not just which single product
- **Local Service (Phoenix) mini-panel** — top 5 keywords by volume from the Local Service tab, since Phase 2 stays visible even while Phase 1 (own products) is the active focus

**Bottom:**
- **Action This Week** callout (Section 3)
- **Priority score trend line** — top 5–8 *current* products, plotted across all available History runs, so rising/fading momentum is visible before it shows up as a rank change
- Freshness/footnote line: any signal that failed or was skipped, cache ages, link references to the raw tabs for drill-down

## 4. "Action This Week" — exact rules

Cap at 5 bullets total, in this fixed order, so it reads as a decision list
on a Monday, not another table. Recommend computing this in Python
(`score_demand.py` or `export_to_sheets.py`) before upload rather than as
live Sheets formulas — the rules below need lookback into History, which
is fragile to express as spreadsheet formulas across a growing row range.

1. **Prototype this week** (top priority, cap 3): `priority_score >= 70`
   AND `fit_score >= 60` AND `competition_score <= 60`. High priority,
   genuinely easy to make right now, not oversaturated.
2. **Watch — rising** (cap 3): week-over-week `priority_score` delta from
   History is positive (this run vs. immediately prior run for that
   product) AND `50 <= priority_score < 70`. Not yet strong enough to
   commit to, but moving the right direction. **Requires ≥ 2 History runs
   for a given product** — if only one run exists, this rule can't fire
   for that product; state "insufficient history" rather than silently
   omitting it, so it's clear why nothing showed up early on.
3. **Needs more data** (cap 2): `keywords_with_data == 0` AND
   `search_volume == 0` AND `community_downloads == 0` — i.e. every
   automated source came back empty. This is a keyword-tuning flag, not a
   "no demand" verdict — word it that way explicitly in the callout text.
4. **Reconsider / drop** (cap 2): `priority_score < 30` for **3
   consecutive** History runs for that product. Prevents `products.yaml`
   from silently accumulating dead weight; this is a prune suggestion, not
   an automatic deletion — the human still decides.
5. **Local service note** (0 or 1, optional): if any Local Service keyword
   crosses `search_volume > 50` with `competition_index` in the "low"
   band (exact threshold is DataForSEO's own competition_index scale —
   Grok should use whatever band DataForSEO already labels LOW, not invent
   a new cutoff), surface one line as a Phase 2 reminder. This is
   deliberately the lowest-priority bullet — Phase 1 (own products) is the
   active focus per `PROJECT_BRIEF.md`.

If a category has zero qualifying bullets in a given week, that's a valid
output — "Nothing crossed the bar this week" is a real, useful signal, not
a bug to paper over with a filler recommendation.

## 5. Data-cleaning & historical-tracking rules

**Join-key integrity.** `product` is the join key everywhere. Any signal
CSV row whose `product` value doesn't match a name in
`config/products.yaml` must be flagged, not silently merged as a new
ghost row — the current `_merge_on_product` outer-join in `score_demand.py`
will happily create one if a name ever drifts (typo, trailing whitespace,
a scanner truncating a name). Recommend `export_to_sheets.py` cross-check
every incoming `product` value against the current products.yaml list and
write unmatched rows to a small "Unmatched — check names" note area rather
than letting them appear as phantom products on the Dashboard.

**Renames break history — don't.** If a product's `name` in
`products.yaml` changes, its History rows under the old name do not
automatically link to the new name (and shouldn't be force-merged — that
silently rewrites the past). Convention: retire the old product (let it
age out via the "Reconsider/drop" rule) and add the renamed version as a
new product line. Note this in `products.yaml` comments when it happens.

**Zero vs. blank vs. skipped.** A `0` in a signal column should mean "we
looked and found nothing," not "we didn't look." When a source is skipped
for a run (Reddit default-off / no `INCLUDE_REDDIT=1`, an X API failure
falling back to manual log, etc.), the corresponding Sheet cells should
render **blank**, not `0` —
`score_demand.py` already tracks this distinction internally via its
`demand_unused` weight-redistribution list; that same list should drive
which columns get left blank on export instead of re-deriving "was this
empty" from the zero values after the fact.

**Category must never be blank.** `score_demand.py` defaults missing
category to `""`, which breaks category-based charts and grouping (chart
3 in particular). Any row exported with blank category should be flagged
the same way as an unmatched product name — surfaced, not silently
charted as an "(none)" bucket.

**Numeric formatting.** All `*_score` columns: 1 decimal. `cpc_avg` /
CPC figures: 2 decimals, currency format. `search_volume` and count
columns: integers, no decimals. `trends_recent_vs_prior_pct_change`:
percentage format.

**History retention.** Append-only, no deletion. At weekly cadence with
~20–30 tracked products, that's roughly 1,000–1,500 rows/year — trivial
for Sheets. No archiving needed now; revisit only if it becomes a real
problem (flagging as a non-issue so it isn't over-engineered up front).

**One canonical run-metadata source.** Every regenerated tab (Dashboard,
Product Rankings, Scoring Detail, Search Volume, Marketplace, Local
Service) must display the *same* `run_date`/`run_time` value for a given
run, read from one place (a small fixed cell range on Dashboard, or a
dedicated thin "Run Meta" tab — implementer's choice). This is what makes
the freshness indicator and "sources active" chips trustworthy — if two
tabs can show different timestamps, a partial-failure run becomes
invisible.

## 6. Acceptance criteria (for Grok to implement against)

1. `export_to_sheets.py` runs as the final step of `run_all.sh`,
   authenticates via a Google Service Account (credentials path from
   `.env`, not committed — follows the existing `.env.example` pattern),
   and writes to one configured spreadsheet ID.
2. All 8 tabs from Section 1 exist, in that order, with header rows frozen
   and column headers matching the names specified above exactly.
3. Product Rankings contains only the trimmed column set in 1.2 — full raw
   scoring columns live in Scoring Detail, not mixed into Product
   Rankings.
4. History is verifiably append-only: running the export twice back-to-back
   increases History's row count by exactly the number of tracked
   products each time; no existing History row is ever modified or
   removed by the export.
5. Every regenerated tab shows an identical `run_date`/`run_time`, sourced
   from one place (Section 5).
6. All 5 charts in Section 3 exist, are bound to live ranges, and the
   trend chart (#4) picks up new History rows on future runs without a
   manual re-bind.
7. Cells for a skipped/failed source render blank, not `0` — verified by
   a default `./run_all.sh` (Reddit off without `INCLUDE_REDDIT=1`) and
   confirming Reddit-related cells are empty (not zero) and the
   Dashboard's "sources active" chip for Reddit shows skipped.
8. Action This Week (Section 4) is generated from the exact rules and
   thresholds specified — verified by checking the output changes
   correctly across two consecutive weekly runs with different underlying
   scores (not static/hardcoded text).
9. Config tab is a regenerated mirror of `config/products.yaml` +
   `config/local_service.yaml` at run time, clearly labeled read-only.
10. No secrets (service account key, API tokens) are committed to the
    repo — loaded via `.env` / a local credentials file path, consistent
    with the existing `.gitignore`.
11. `./run_all.sh` completes end-to-end including the Sheets export with
    no manual steps, and runs cleanly under the existing
    `com.demandmonitor.weekly` launchd job.
12. Subjective but real bar: opening the Dashboard tab alone (no other
    tabs) should answer "what do I work on this week" — if the owner has
    to open Product Rankings or Scoring Detail to answer that question on
    a normal week, the Dashboard isn't done.
